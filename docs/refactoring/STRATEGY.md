# SAGE strategy proposal: protocol-first, multi-repository, deterministic

Status: proposal, 2026-09-11. This document synthesises everything gathered in this effort and answers the maintainer's stated direction:

1. classify and understand the documentation (see `DOCS_GRAPH.md`),
2. split the monolith into reusable, open-source-friendly repositories,
3. find security features that are implemented but not connected (see `SECURITY_WIRING_AUDIT.md`),
4. make agent-to-agent and agent-to-MCP call/response structures tamper-evident with deterministic signing and verification, easy to adopt from agent clients (Codex, Claude Code, Hermes and others), with a core library that language SDKs can build on,
5. be open-source friendly with supply-chain-resistant CI and real version management (see `SUPPLY_CHAIN_AUDIT.md`).

Inputs: `graph/summary.md`, `graph/entrypoints.md`, `FEATURE_MAP.md`, `analysis/01..05`, `REFACTORING_DESIGN.md`, `DECISIONS.md`, `DOCS_GRAPH.md`, `SECURITY_WIRING_AUDIT.md`, `SUPPLY_CHAIN_AUDIT.md`, and an inspection of the other repositories in the SAGE-X-project organisation (`sage-a2a-go`, `sage-multi-agent`, `sage-adk`, `rs-sage-core`, `sage-proxy-server`).

---

## 1. Where the project stands (facts that drive the proposal)

### What SAGE is for

SAGE's purpose, restated from the maintainer: when an AI agent calls another agent, calls an MCP server, or is called by one, the request and the response must not be forgeable, replayable or silently altered, and any agent client should be able to adopt that protection without re-implementing cryptography. Signing and verification are deterministic operations, so the protocol must be specified so that every implementation produces and accepts exactly the same bytes.

Two conclusions follow. First, the repository is not "one project with too many features" so much as one project with one working feature set (Go library + CLI + contracts) surrounded by unfinished parallel attempts (four SDKs, cgo lib, second handshake, second Rust core in another repo). Second, the protection the project promises is not yet enforced on the paths consumers actually use; splitting repositories before fixing that would copy the gaps into several places.

## 2. Target shape

### Design principle: protocol first, cores second, bindings third

The deterministic guarantee the maintainer wants cannot live in a library; it lives in a specification plus conformance vectors that every implementation must reproduce byte for byte. Once that exists, the number of implementations stops mattering for correctness, and language coverage becomes a packaging question.

```
Tier 0  sage-spec          normative wire formats + JSON test vectors        (no code beyond a vector verifier)
Tier 1  sage (Go)          reference implementation, CLIs, Go consumers      (native Go, no FFI)
        sage-core (Rust)   portable core: C ABI + WASM, passes the vectors   (from rs-sage-core)
Tier 2  sage-sdk-*         thin bindings over sage-core (Python, TS, Java)   (uniffi / napi-rs+wasm / Panama)
        sage-gateway       zero-integration sidecar for agent clients + MCP  (Go, built on sage)
Tier 3  sage-contracts     Solidity + Solana + published ABIs and bindings
```

### 2.1 `sage-spec` (new repository; Apache-2.0)

Contents:

- **RFC 9421 agent profile.** Mandatory covered components: `@method`, `@target-uri`, `@authority`, `content-type`, `content-digest` (RFC 9530, SHA-256), `sage-did`; signature parameters `created`, `expires`, `nonce`, `keyid` (= DID key hash), `alg` from a fixed table (`ed25519`, `ecdsa-secp256k1-keccak256` or `ecdsa-secp256k1-sha256` chosen once, `ecdsa-p256-sha256`). Verifiers reject any signature that does not cover the mandatory set. This closes the body-replacement and replay findings by specification rather than by option.
- **Canonicalisation rules.** Header names lowercase; RFC 3339 UTC seconds; JSON payloads canonicalised with JCS (RFC 8785) wherever a JSON structure is signed (A2A card proofs, MCP envelopes); ECDSA with RFC 6979 nonces and low-S normalisation; fixed base64url without padding; one signature label. Verification is a pure function of (bytes, public key, policy, clock) and never performs network I/O; key resolution is a separate, cacheable step.
- **HPKE 1-RTT profile.** The existing constants (`hpke-base+x25519+hkdf-sha256`, info/export labels, ack/cb/c2s/s2c labels) written down, plus one mandatory session AEAD. Recommendation: AES-256-GCM as mandatory (WebCrypto, JCA, BouncyCastle, `aes-gcm`, Go stdlib all provide it), ChaCha20-Poly1305 optional. The Go core adds AES-GCM; the Rust core already uses it. Message counter and direction are part of the AEAD nonce/AAD so replay and reordering are rejected at the session layer.
- **`did:sage` method.** DID grammar (one parser), resolution against AgentCardRegistry (active flag, key `verified` flag, revocation, KEM key), caching policy.
- **MCP binding.** How a JSON-RPC 2.0 message is protected: a `_meta.sage` (or transport-header) envelope carrying `did`, `keyid`, `created`, `expires`, `nonce`, and a signature over JCS(`method`, `params` or `result`/`error`, `id`) plus the tool/server identity. Covers both directions: agent → tool call, tool → result (so a malicious tool result cannot be swapped by an intermediary) and server-initiated calls to the agent (sampling, elicitation).
- **Test vectors.** JSON files generated by the Go reference: key pairs, signature bases, signatures, HPKE transcripts, session ciphertexts, card proofs, MCP envelopes, plus negative vectors (replayed nonce, expired `created`, altered body, wrong key). Every implementation runs them in CI.

### 2.2 `sage` (this repository, Go)

Keeps: `pkg/agent/*` at current import paths (Decision 2), `cmd/sage-crypto`, `cmd/sage-did`, `cmd/sage-verify`, examples, Go docs. Adds: `pkg/agent/conformance` (vector runner), AES-GCM session suite, MCP envelope package. Removes: `sdk/`, `lib/`, `contracts/` (moved), `handshake` (Decision 1), `tests/random`, `core/message/*`, `crypto/vault`. Applies the `REFACTORING_DESIGN.md` phases with the adjustments in `DECISIONS.md`. Stays the reference implementation because the two active consumers and the CLIs are Go and because it is the implementation the vectors are generated from.

### 2.3 `sage-core` (Rust, from `rs-sage-core`)

Becomes the portable core for every non-Go language: `cdylib` with a stable C header, `uniffi` bindings (Python, Kotlin, Swift), `wasm-bindgen` for TypeScript/browser, `napi-rs` for Node if a native addon is preferred over WASM. Must pass the spec vectors; the divergent session layer is realigned to the spec. Keep MIT OR Apache-2.0. Remove its 4-phase handshake and blockchain feature gates that duplicate Go unless a Rust consumer appears. Publishing: crates.io, prebuilt binaries per platform attached to releases with SLSA provenance, so SDKs can vendor them.

Why Rust rather than the Go `c-shared` route the maintainer floated: a Go shared library embeds the Go runtime in the host process (signal handling, thread model, roughly 10 MB), has no usable browser/WASM path for TypeScript, and cannot be consumed by Rust or by Java Panama without the same runtime cost; the Rust core already exists, already exports C and WASM surfaces, and its licence is SDK-friendly. Cost: two cores to maintain. Mitigation: the vectors, and a policy that any protocol change lands in `sage-spec` first with vectors before either core implements it.

### 2.4 `sage-sdk-python`, `sage-sdk-typescript`, `sage-sdk-java` (new repositories)

Thin bindings over `sage-core` plus idiomatic helpers (HTTP client middleware that signs outgoing requests and verifies responses; MCP client/server wrappers). The current `sdk/*` directories are archived, not migrated: none of them implements the protocol. TypeScript ships as WASM + N-API optional; Python as wheels with the bundled core; Java via Panama FFI (JDK 22+) or JNA with bundled natives. Each SDK's CI runs the spec vectors; that is the interoperability guarantee, replacing the current unverifiable claims.

### 2.5 `sage-gateway` (new, Go; the `sage-proxy-server` repository can host it)

The adoption path for agent clients that cannot or should not link a library: Codex, Claude Code, Hermes and similar tools already speak MCP and HTTP through configuration. `sage-gateway` runs locally as

- an **MCP wrapper**: launches or connects to an MCP server (stdio or HTTP), signs every result it returns to the agent, and verifies every call before forwarding; the agent client only changes its MCP config to point at the wrapper;
- an **HTTP forward proxy / reverse proxy**: signs outgoing agent requests (RFC 9421 profile) and verifies inbound ones, with DID resolution and caching;
- an **A2A endpoint** implementing the HPKE 1-RTT handshake and encrypted sessions for agent-to-agent traffic, i.e. the server that `api/openapi.yaml` promised.

This is where "easy to apply" is won: one binary, one config line, no SDK. The SDKs remain for teams that embed SAGE in their own agent code.

### 2.6 `sage-contracts`

Solidity, Solana, Hardhat/Foundry tests, deployment records, and a CI job that publishes ABIs and regenerates Go (`abigen`) and Rust (`alloy`) bindings on tag. Consumers pin a contracts tag; the bindings drift found in `analysis/05` disappears because bindings are build outputs, not hand-maintained sources.

### 2.7 Repository dependency direction

```mermaid
graph LR
  SPEC[sage-spec\nvectors] --> GO[sage (Go)\nreference + CLIs]
  SPEC --> RS[sage-core (Rust)\nC ABI + WASM]
  CON[sage-contracts\nABIs, bindings] --> GO
  CON --> RS
  RS --> PY[sage-sdk-python]
  RS --> TS[sage-sdk-typescript]
  RS --> JV[sage-sdk-java]
  GO --> GW[sage-gateway\nMCP wrapper + proxy + A2A]
  GO --> A2A[sage-a2a-go]
  GO --> MA[sage-multi-agent]
  GW -. config only .-> CLIENTS[Codex / Claude Code / Hermes / any MCP client]
```

Rules: arrows only point downward; no repository imports a sibling at the same tier; every repository pins the spec version it implements and runs the vectors for that version.

## 3. Determinism: what "deterministic signing and verification" requires in code

| Requirement | Today | Target |
|---|---|---|
| Signature base is a pure function of the message | HTTP path: signer chooses components; `RequiredComponents` unused; map iteration selects among multiple signatures (`verifier_http.go:143-147`); query parameters URL-decoded during canonicalisation (`canonicalizer.go:178-185`) | mandatory component set; single signature label; canonicalisation rules from spec; byte-exact vectors |
| Same key type hashes the same way everywhere | secp256k1 `KeyPair.Sign` uses Keccak-256, envelope verifier uses SHA-256 | one algorithm identifier per key type in the spec table; both cores implement exactly it |
| ECDSA signatures reproducible | secp256k1 via go-ethereum (RFC 6979) yes; P-256 via `crypto/ecdsa` random nonce, no low-S | RFC 6979 + low-S for all ECDSA |
| Structured payloads have one byte form | A2A card proof uses Go `encoding/json` (HTML escaping, `omitempty`, time precision) (`a2a_proof.go:86,182`); HPKE response signs a struct but sends a map (`hpke/server.go:344-360`) | JCS (RFC 8785) for every signed JSON; sign the bytes that are sent |
| Verification has no hidden inputs | `time.Now()` inside verification; DID resolution inside `VerifyAgentMessage` | clock injected; resolve-then-verify split; verification offline and cacheable |
| Replay is impossible by construction | nonce parsed, never checked on the HTTP path; sessions accept the same ciphertext repeatedly | nonce + `created`/`expires` window enforced by the verifier; session AEAD nonce derived from a monotonic counter with direction in AAD |

## 4. Threat coverage for agent / MCP traffic after the change

| Threat | Today | After |
|---|---|---|
| Tampering with request or response body in transit | Not covered on the HTTP path (body swap verifies) | `content-digest` mandatory; MCP envelope signs JCS(params/result) |
| Replay of a signed request or tool result | Not covered | nonce store on the verifier path + time window; session counters |
| Impersonation of an agent DID | Partly (signature checked against resolved key; `verified`/revocation flags ignored) | resolver enforces active + verified + not revoked; keyid bound to DID key hash |
| Malicious tool result injected into an agent | Not covered (nothing signs MCP results) | gateway/SDK signs results with the tool server's DID; agent verifies before use |
| Confused deputy through an MCP server calling back into the agent | Not covered | envelope includes direction and target identity; server-initiated calls are verified like any other |
| Downgrade to unsigned traffic | Not covered (verification optional) | policy in gateway/SDK: reject unsigned from known DIDs; spec-level "signature required" for A2A |
| Key compromise / rotation | Rotation exists for two key types; no revocation on resolve | on-chain revoke honoured by resolver cache invalidation; rotation for all key types |
| Denial of service on the verifier | No body size limits, unbounded nonce store in HPKE | size limits in gateway; bounded, TTL-evicting nonce store from the spec |

## 6. Versioning and release policy across repositories

- **Semver per repository.** `sage-spec` versions the protocol (`v1.0.0` = today's fixed profile). Cores and SDKs declare `spec: 1.x` in their manifests and run that version's vectors; a spec major bump is the only event that forces a coordinated release.
- **Go module tags** in `sage` (`v1.6.0`, `v1.7.0`, …); no `/v2` path move (Decision 2). Deprecated symbols live two minor releases.
- **Contracts** version the ABI (`abi/v4.1.0`); bindings carry the same tag; on-chain deployments are recorded per network in the contracts repository, not in Go code (`NetworkPresets` reads a published JSON).
- **Releases** built by CI only from tags that pass the tag ruleset; binaries and packages signed with Sigstore keyless, SLSA level 3 provenance (`slsa-github-generator`), SBOM (CycloneDX) attached; reproducible Go builds (`-trimpath`, `CGO_ENABLED=0`, pinned toolchain equal to `go.mod`).
- **Changelog** from Conventional Commits via release-please (or `git-cliff` for Rust); the `VERSION` file and `update-version.sh` are replaced by tags.
- **Compatibility matrix** in `sage-spec` README: spec version × core version × SDK version × contracts ABI, updated by the release workflow.

## 7. Licensing

The Go core is LGPL-3.0; the Rust core is MIT OR Apache-2.0; the TypeScript SDK and contracts say MIT; Python and Rust SDK say LGPL-3.0. A library meant to be embedded in many agent runtimes and statically linked (Go, WASM, native addons) is hard to adopt under LGPL. Recommendation: Apache-2.0 for `sage-spec`, `sage-core`, all SDKs and the gateway; relicense the Go core to Apache-2.0 as well, which is feasible now because the history has a single primary author (contributor consent is required from every past contributor before the change).

## 8. Documentation policy after the split

- The spec repository is the single source of truth for protocol behaviour; core and SDK repositories link to it instead of restating it.
- Each repository keeps only: README (what it is, install, one example), CONTRIBUTING, SECURITY, CHANGELOG, and reference docs generated from code. Guides live in a docs site built from the repositories at tag time.
- Stale documents identified in `DOCS_GRAPH.md` are removed with the code they describe (V2/V4 clients, 4-phase handshake, `cmd/sage-server`, SDK interoperability claims); planning and audit reports move to an `archive/` directory with a date prefix.

## 9. Alternatives considered

| Alternative | Why not (trade-off) |
|---|---|
| Go core compiled as `c-shared` and used by every SDK through FFI (the maintainer's initial idea) | Single core to maintain, but the Go runtime rides inside every host process, TypeScript/browser has no viable path (Go WASM is large and single-threaded), Rust consumers gain nothing, and per-platform cgo distribution is the hardest packaging story of the three. Kept only as an optional artifact if a C consumer appears. |
| Native implementation per language against the spec, no shared core | No FFI packaging at all and the best fit for each ecosystem, but four or five independent cryptographic implementations to audit and keep in sync; only acceptable once vectors exist and only for languages with mature RFC 9421 + HPKE libraries (TypeScript and Python qualify; Java less so). Retained as an allowed path per SDK, not as the default. |

## 10. Risks and open points

- Two cores (Go, Rust) is a maintenance commitment; without the vectors and the "spec first" rule they will diverge again as they already have at the session layer.
- Rust maintainership: `rs-sage-core` last changed 2025-11; the plan needs an owner for it.
- Bus factor: one primary author; the governance step (reviews, CODEOWNERS) has to be sized for the team that exists.
- MCP binding design (§2.1) is new work that must be validated against MCP's own evolution (transport headers vs `_meta`); prototype in the gateway before freezing it in the spec.
- Kaia AgentCard deployment address is unknown; until confirmed the Kaia preset stays empty.

## Facts vs. opinions

**Fact**
- `sage-a2a-go` and `sage-multi-agent` build against current `main`; `sage-adk` imports paths removed in v1.0.
- `rs-sage-core` builds with the `ffi` feature and passes 746 unit/integration tests (2 doctests fail); it uses AES-256-GCM sessions and lacks the Go session HKDF labels; no cross-implementation vectors exist.
- An RFC 9421 request signed with the example component set verifies after its body is replaced; HPKE-derived sessions have a zero signing key; secp256k1 `KeyPair.Sign` (Keccak-256) signatures fail the SHA-256 envelope verifier (all executed in `SECURITY_WIRING_AUDIT.md` §8).
- Ruleset `main` (id 8640770) has `include: []`; `GET /rules/branches/main` returns `[]`; `security.yml` is `disabled_inactivity`; secret scanning and push protection are `disabled`; 6 collaborators have push.
- No repository in the organisation serves `/debug/kem-pub`, `/debug/server-did`, `/debug/register-agent` or `/v1/a2a:sendMessage`; `sage-proxy-server` is an empty initial commit.

**Opinion**
- [High] Fixing governance and wiring the existing controls in the current repository must precede any repository split; otherwise the split copies unenforced security into several places.
- [High] A specification with byte-exact vectors is the only mechanism that makes "deterministic verification" true across languages; libraries alone cannot guarantee it.
- [High] The Rust core is the right FFI/WASM base for non-Go SDKs; the Go `c-shared` route is worse on runtime, browser reach and packaging.
- [Mid] AES-256-GCM as the mandatory session AEAD maximises SDK reach; ChaCha20-Poly1305 can stay optional. This is a spec decision to confirm with a short review.
- [Mid] A local gateway (MCP wrapper + proxy) is the fastest path to protecting Codex/Claude Code/Hermes-style clients, because those clients are configured, not programmed.
- [Low] Relicensing the Go core to Apache-2.0 is feasible given the author history; it still needs an explicit consent check.
